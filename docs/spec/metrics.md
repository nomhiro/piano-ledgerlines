## 0. 設計思想

### 0.1 スコアは目的ではない

> スコアは**練習箇所を特定するためのインデックス**であり、演奏の価値を決めるものではない。

したがって以下を守る。

| 守ること | 理由 |
|---|---|
| 総合点よりも小節別の内訳を主役にする | 「82点」は行動につながらない。「19小節のリズムが54点」は行動につながる |
| 高得点を出しにくくしない | 減点法で萎縮させない。上限に張り付いてもよい |
| 音楽的に正しい逸脱を減点しない | ルバート、アゴーギク、意図的な間は「ミス」ではない |
| 指標間の独立性を保つ | 1つのミスが全指標を下げると、原因が分からなくなる |

### 0.2 「正解」は楽譜そのものではない

楽譜どおりに機械的に弾くことが最高得点になる設計は、音楽的に誤りである。
本プロダクトは以下の階層で「ずれ」を扱う。

```
ずれ
├─ 誤り (error)        … 抜け音・余分な音・明確なリズムの間違い → 減点する
├─ 揺らぎ (deviation)  … 微小なタイミング差・音量差            → 許容範囲を設けて減点しない
└─ 表現 (expression)   … 局所的で音楽的に整合したテンポ/音量の変化 → 減点しない（検出して称賛する）
```

「揺らぎ」と「表現」を「誤り」と誤認しないことが、中上級者に受け入れられる分水嶺である。

## 1. 入力データ

指標算出は、[分析パイプライン](../design/analysis-pipeline.md) の出力である
以下3つのデータ構造を入力とする。

### 1.1 参照譜 (Reference Score)

MusicXML から繰り返しを展開して得た「演奏順の音符列」。

```ts
interface RefNote {
  id: string;
  measure: number;          // 展開後の演奏順小節番号
  scoreMeasure: number;     // 楽譜上の小節番号（表示用）
  onsetBeat: number;        // 曲頭からの累積拍
  durationBeats: number;    // 記譜上の音価
  midi: number;             // 音高
  voice: number;            // 声部
  staff: 1 | 2;             // 大譜表の上下（≒右手/左手）
  tie: "none" | "start" | "stop" | "continue";
  // 記譜された表現指示
  dynamicMark: string | null;      // "p" | "mf" | "ff" ...（直前の有効な指示）
  hairpin: "cresc" | "dim" | null;
  articulation: ("staccato" | "tenuto" | "accent" | "marcato")[];
  slurred: boolean;                // スラーの内側にあるか
  pedalMark: { down: boolean; up: boolean } | null;
}

interface RefMeasure {
  measure: number;
  scoreMeasure: number;
  startBeat: number;
  beats: number;                   // 拍数（拍子から）
  tempoBpm: number;                // 記譜テンポ（なければ曲の目標テンポ）
  tempoText: string | null;        // "rubato" | "rit." | "a tempo" ...
  hasDynamicMark: boolean;
  hasArticulationMark: boolean;
  hasPedalMark: boolean;
}
```

### 1.2 演奏 (Performance)

採譜結果（音声→MIDI）、または MIDI 入力そのもの。

```ts
interface PerfNote {
  id: string;
  onsetSec: number;
  offsetSec: number;
  midi: number;
  velocity: number;         // 0-127
  confidence: number;       // 0-1 採譜の確信度
}

interface PedalEvent {
  type: "sustain";
  downSec: number;
  upSec: number;
  confidence: number;
}
```

### 1.3 アライメント (Alignment)

参照譜と演奏の対応付け結果。

```ts
type MatchKind = "matched" | "missed" | "extra";

interface Match {
  refNoteId: string | null;   // extra のとき null
  perfNoteId: string | null;  // missed のとき null
  kind: MatchKind;
  onsetErrorSec: number | null;  // perf - 期待時刻。matched のみ
}

interface BeatMap {
  // 曲頭からの累積拍 → 実演奏の秒。区分線形。
  beatToSec(beat: number): number;
  secToBeat(sec: number): number;
  /** 小節ごとの実測テンポ */
  measureTempo: { measure: number; bpm: number }[];
}

interface AlignmentResult {
  matches: Match[];
  beatMap: BeatMap;
  measureConfidence: { measure: number; confidence: number }[];
  playedRange: [number, number];   // 実際に演奏された小節範囲
}
```

**BeatMap が本設計の要**である。演奏の絶対時刻を「拍」に変換することで、
テンポが揺れていてもリズムを正しく評価できる。

## 2. 共通の枠組み

### 2.1 スコアの構造

```
テイク
├─ overallScore: 0-100          … 5指標の重み付き平均
├─ metrics: {5指標}: 0-100      … 小節スコアの加重平均（音符数で重み付け）
└─ measureScores: [
     { measure, score: 0-100, metrics: {5指標}, confidence: 0-1 }
   ]
```

- **小節が先、全体が後**。すべての指標はまず小節ごとに算出し、それを集約して全体スコアにする
- 集約時の重みはその小節の**参照音符数**（音符の多い小節の影響を大きくする）

### 2.2 減点関数

各指標は「誤差量 → 0-100」の変換に共通の関数を使う。

```
score(e) = 100 * exp( -(e / τ)^k )
```

| 記号 | 意味 |
|---|---|
| `e` | 誤差量（指標ごとに定義） |
| `τ` | 許容スケール。`e = τ` のとき約 37 点（k=1） |
| `k` | 形状。k=1 で指数、k=2 でガウシアン（小さな誤差にさらに寛容） |

**指数減衰を使う理由**: 線形減点だと「小さなミスの積み重ね」で不当に低くなる。
指数関数なら、微小な誤差はほぼ満点、大きな誤差だけを明確に落とせる。

### 2.3 デッドゾーン

多くの指標に「この範囲内は完全に無視する」不感帯を設ける。

```
e_eff = max(0, e - deadzone)
```

人間の知覚限界（例：タイミングの弁別閾は約 20-30ms）を下回る差で減点しない。

### 2.4 評価対象外 (N/A)

以下の場合、その指標はその小節で **N/A** とし、集約から除外する。

| 指標 | N/A になる条件 |
|---|---|
| `dynamics` | 曲全体に強弱記号が1つもない／AGCが無効化できなかった（ダイナミックレンジ < 10 dB） |
| `pedal` | 曲にペダル記号がない／ペダル検出の信頼度が閾値未満 |
| すべて | 小節の `confidence < 0.5`（→ [7章](#7-信頼度)） |
| すべて | 小節に参照音符が存在しない（休符のみ） |

N/A が発生した場合、総合スコアの重みは**残った指標で正規化**する。

> **上表の「すべて | 小節の `confidence < 0.5`」は現在の動作ではない。** 実装は
> 小節単位の confidence 閾値ではなく、指標ごとに `scored` / `withheld` / `unavailable`
> を決める（→ [7.2](#72-閾値と挙動)）。この行は 7.2 で「未較正の設計仮説」として
> 明示的に残している未実装のアイデアであり、削除はしないが、現在の N/A 判定の
> 仕組みとしては読まないこと。

### 2.5 指標の重み（総合スコア）

| 指標 | 重み | 根拠 |
|---|---|---|
| `pitch` | 0.28 | 最も基礎。ここが崩れていれば他の議論に進めない |
| `rhythm` | 0.28 | 音程と並ぶ基礎 |
| `tempo` | 0.17 | 通し演奏の完成度に直結。録音条件に最も頑健（M4 実測 ±3点以内） |
| `dynamics` | 0.17 | 表現の中核 |
| `pedal` | 0.10 | M4 で実用精度を確認（劣化条件でも F1 0.81）。当初 0.08 から引き上げ |

> `articulation`（旧 0.12）は M4 の検証により **MVP から除外した**。
> マイク録音では音符の消音時刻が取得できない → [3.5](#35-articulation--アーティキュレーションmvp-から除外)
> 空いた重みは上記5指標に再配分している。

> 重みは**曲のステータスによって変えない**。譜読み段階でも同じ物差しで測ることで、
> 「同じ尺度で伸びている」ことを可視化できる。

### 2.6 絶対スコアの扱い（M4 の実測を受けて）

**同じ演奏でも、録音環境が変われば絶対スコアは大きく動く。**
M4 で同一の演奏を4つの録音条件で解析したところ、次の変動が観測された。

| 条件 | overall | pitch | rhythm | tempo | dynamics | pedal |
|---|---|---|---|---|---|---|
| clean（基準） | 88.9 | 85.2 | 87.0 | 92.4 | 91.2 | 94.9 |
| 部屋の残響+ノイズ | -15.7 | **-37.7** | -11.8 | -2.7 | -5.7 | -4.5 |
| スマホ録音 | -14.7 | **-37.6** | -6.6 | -1.9 | -9.0 | -5.0 |
| スマホ録音+AGC | -27.7 | **-50.0** | -14.7 | -3.2 | **-45.1** | -13.5 |

採譜の note F1 が 0.98 → 0.83 に落ちると、その取りこぼしがそのまま
「弾き逃し」「余分な音」として計上されるためである。

> **したがって、絶対スコアを UI の主役にしてはならない。**
>
> | 何を見せるか | 位置づけ |
> |---|---|
> | 前回テイクとの差分、小節別ヒートマップの推移 | **主役**。同一環境なら採譜誤差は共通のバイアスとして乗るため、差分は演奏差を反映する |
> | `tempo` / `pedal` の絶対値 | 参考値として提示してよい |
> | `pitch` / `rhythm` / `dynamics` の絶対値 | 環境依存が大きい。**他人との比較には使わない** |
>
> 録音環境が前回から変わったことを検出した場合（→ [7.4](#74-録音品質の推定)）、
> 「今回は録音環境が違うため、前回との比較は参考程度に」と明示する。

### 2.7 差分の測定ノイズ（M4.5 の実測）

2.6 は「差分なら演奏差を反映する」と述べた。M4.5 でその前提を検証した。

**測り方**: 同一の演奏音源に対し、録音条件の設定は変えずに**乱数の実現値だけ**を振り直し、
4曲 × 5回ずつ採譜・アライメント・採点した。演奏はまったく同じなので、
出てきたスコアのばらつきは**すべて測定ノイズ**である。

- `noise` 水準 — 雑音の実現値のみが変わる（同じ部屋・同じマイク位置での録り直しに相当）
- `session` 水準 — 加えて残響 ±15%・マイク位置 ±25%・SNR ±3dB を振る（別の日の練習に相当）

**MDD（最小検出可能差）** = 1.96·√2·σ。
2つのテイクの差がこれを下回るなら、演奏が変わった証拠にならない。

| 指標 | σ (noise) | **MDD (noise)** | σ (session) | **MDD (session)** |
|---|---|---|---|---|
| **overall** | 2.96 | **8.2** | 2.24 | **6.2** |
| `pitch` | 7.22 | **20.0** | 4.05 | **11.2** |
| `rhythm` | 3.81 | 10.6 | 4.00 | 11.1 |
| `tempo` | 1.25 | 3.5 | 2.52 | 7.0 |
| `dynamics` | 2.25 | 6.2 | 2.94 | 8.1 |
| **`pedal`** | **1.61** | **4.5** | **1.53** | **4.2** |

> **総合スコアの差が6点未満なら「横ばい」と扱う。**
> 「先週72点 → 今週76点」は改善ではない。
> UI では MDD 未満の差分に矢印や色を付けてはならない（→ [機能仕様 F-08](./functional.md#f-08-分析結果画面の構成)）。

わかったこと。

| 観察 | 含意 |
|---|---|
| **`pedal` が最も安定**（MDD 4点台）、`tempo` も比較的安定 | 「ペダルが良くなった」は少ないテイク数で言える |
| **`pitch` が最も不安定**（MDD 11〜20点） | 音程の改善は単発のテイク比較で見せない。複数テイクを束ねた推移でのみ提示する |
| 曲によって σ が4倍以上違う。**スコアの低い曲ほどばらつきが大きい** | 曲ごとにノイズを推定する。全曲一律の閾値は使えない |
| `noise` と `session` の差は有意でない（n=5） | 録音環境の細かい違いより、**採譜そのもののゆらぎ**が支配的 |

**設計への反映**

1. 差分には**信頼区間を併記**する。幅は録音品質（→ [7.4](#74-録音品質の推定)）と曲の難易度から推定する。
2. **複数テイクを束ねた比較**（週次、直近3テイクの平均）を既定の比較単位にする。
   n テイクの平均をとれば MDD は 1/√n になる。3テイクなら総合の MDD が 6.2 → 3.6 点まで下がる。
3. AI 講評には**差分そのものではなく「有意な差分」だけ**を渡す。
   ノイズを根拠に「音程がかなり改善しました」と書かせてはならない。

> **この検証の限界**: n=5 は σ の推定として少なく（相対誤差 35%）、
> 音源は MAESTRO の4曲のみ、劣化は合成である。実機での再測定が要る。
> → [m45-report.md 3章](../poc/m45-report.md#3-差分の安定性)

## 3. 指標定義

### 3.1 `pitch` — 音程正確性

**問い**: 楽譜どおりの音を鳴らせているか。

#### 誤差量

小節 *m* について、

| 記号 | 定義 |
|---|---|
| `N_ref` | 参照音符数 |
| `n_missed` | `kind = "missed"` の数（抜け音） |
| `n_extra` | `kind = "extra"` の数（余分な音） |

```
e_pitch = (w_miss * n_missed + w_extra * n_extra) / N_ref
```

| 係数 | 値 | 理由 |
|---|---|---|
| `w_miss` | 1.0 | 音が抜けるのは明確な誤り |
| `w_extra` | 0.7 | 隣接鍵の巻き込みは音楽的損失がやや小さい |

**ただし `n_extra` の判定に例外を設ける。**

| 例外 | 扱い |
|---|---|
| 装飾音・アルペジオ的な追加（参照音の直前 100ms 以内に、その音の 1〜2 半音下） | `extra` としない（演奏解釈） |
| ペダル残響による重複検出 | アライメント段で除去済みとする |
| オクターブ違い（`midi` が ±12 でマッチ可能） | `missed + extra` ではなく `octave-error` として `w = 0.8` の単一エラーにする |

#### スコア

```
pitch = 100 * exp( -(e_pitch / 0.15)^1 )
```

`τ = 0.15` は「音符の15%を外すと約37点」に相当する。

#### 補足

`velocity` が極端に低い音（`< 15`）は「触れただけ」とみなし、
参照音符とマッチしても `matched` ではなく `weak-touch` として `w = 0.5` の部分減点にする。

---

### 3.2 `rhythm` — リズム

**問い**: 各音の発音タイミングが、譜面の音価どおりの比率になっているか。

#### 誤差量

**テンポの揺れを除去したうえで**評価する。これが `tempo` 指標との分離点である。

各 matched 音符について、BeatMap を用いて演奏時刻を拍に逆変換する。

```
b_perf(i) = beatMap.secToBeat( onsetSec(i) )
b_ref(i)  = refNote(i).onsetBeat
δ(i)      = b_perf(i) - b_ref(i)        [拍単位]
```

BeatMap は小節単位のテンポ変動を吸収するため、`δ` は**小節内の相対的なリズムのずれ**だけを表す。

小節内の系統的なオフセット（小節全体が少し遅れて始まる等）も除去する。

```
δ'(i) = δ(i) - median{ δ(j) | j ∈ 小節m }
```

デッドゾーンを適用したうえで RMS を取る。

```
e_rhythm = sqrt( mean_i( max(0, |δ'(i)| - d_r)^2 ) )
d_r = 0.03 拍                          … 約 15ms @ ♩=120。知覚閾以下
```

> **M4 の実測を受けた補正**: 劣化録音（スマホ・残響下）では採譜の onset MAE が **18 ms** あり、
> `d_r = 0.03 拍`（♩=120 で 15 ms）を超えてしまう。つまり完璧に弾いてもデッドゾーンを
> 突き抜けて減点される。**録音品質の推定値（→ [7.4](#74-録音品質の推定)）が
> 「劣化」を示す場合は `d_r = 0.045 拍` に緩める。**
>
> **実装済み**（`worker/ledgerlines_worker/scoring_constants.py`）: `DEAD_RHYTHM = 0.03`、
> `DEAD_RHYTHM_DEGRADED = 0.045`。切り替え条件は `dynamicRangeDb < DEGRADED_DYNAMIC_RANGE_DB`
> （`= 14.0`）で、`worker_main.py` が `preprocess()` の `dynamicRangeDb` から `degraded`
> フラグを立てて `metrics.compute(..., degraded=True)` に渡す。**この 14.0 は 3.4 の
> AGC 判定閾値（10.0）とは別の指標・別の目的の値であり、同一の数値として扱わない。**

#### スコア

```
rhythm = 100 * exp( -(e_rhythm / 0.12)^2 )
```

`τ = 0.12 拍`（♩=120 で約 60ms）、`k = 2`（ガウシアン）。
小さなずれには非常に寛容、大きなずれで急速に落ちる。

#### 特別扱い

| 状況 | 扱い |
|---|---|
| 両手の縦の揃い（同一拍の音符群の分散） | 別途 `e_sync` として算出し、`e_rhythm` に 0.3 の重みで加算する。**アルペジオ癖の検出に有効** |
| 参照譜に `arpeggiate` 記号がある | `e_sync` を評価しない |
| 装飾音（`grace`） | リズム評価から除外 |
| 3連符・ポリリズム | 通常どおり評価（BeatMap が拍を正しく持つ前提） |

---

### 3.3 `tempo` — テンポ安定

**問い**: 設定テンポに対する揺れが少ないか。**ただし意図的なルバートは減点しない。**

#### 誤差量

BeatMap の `measureTempo` から、小節ごとの実測テンポ `T(m)` を得る。

**Step 1: 基準テンポの推定**

```
T_base = median{ T(m) | m ∈ 演奏範囲 }
```

ユーザー設定の目標テンポではなく**実演奏の中央値**を基準にする。
理由：「全体的に少し遅く弾いた」ことは不安定ではない。それは選択である。

ただし目標テンポとの乖離は別途 `tempoOffset` として記録し、UIに表示する（減点はしない）。

**Step 2: 意図的な変化の除外**

以下を満たす小節は「表現」とみなし、誤差から除外する。

| 条件 | 意味 |
|---|---|
| 参照譜に `rit.` / `accel.` / `rubato` / `a tempo` / フェルマータがある | 記譜された指示 |
| 楽節末（次の小節に強い終止感がある／2重線・複縦線） | 音楽的な間 |
| テンポ変化が**滑らか**（隣接3小節で単調増加または単調減少、かつ変化率が緩やか） | 意図的なアゴーギク |

3つ目の判定：

```
smooth(m) = |T(m) - (T(m-1)+T(m+1))/2| < 0.5 * |T(m+1) - T(m-1)|
```

隣接小節の中点に近い（＝直線的に変化している）なら滑らかとみなす。

**Step 3: 誤差**

除外後の小節集合 `M'` について、

```
r(m) = T(m) / T_base                 … テンポ比
e_tempo = sqrt( mean_{m ∈ M'}( max(0, |ln r(m)| - d_t)^2 ) )
d_t = 0.03                            … ±3% は無視
```

**対数比を使う理由**: BPM の絶対差は基準テンポに依存する（♩=60 の 5 BPM と ♩=180 の 5 BPM は意味が違う）。
対数比なら相対変化として扱える。

#### スコア

```
tempo = 100 * exp( -(e_tempo / 0.10)^2 )
```

`τ = 0.10`（約 ±10% の揺れ）。

#### 小節スコアへの分解

`tempo` は本来テイク全体の性質だが、UI上は小節別に持つ必要がある。
小節 *m* のテンポスコアは、その小節単体の誤差から算出する。

```
tempo(m) = 100 * exp( -( max(0, |ln r(m)| - d_t) / 0.10 )^2 )
```

除外対象の小節は `tempo(m) = N/A` とする。

### 3.4 `dynamics` — ダイナミクス

**問い**: 強弱記号に対する音量差を再現できているか。

#### 前提と限界

音声のみの場合、**絶対音量は意味を持たない**（マイク距離・部屋・ゲインに依存）。
評価できるのは**相対的な音量の形**だけである。したがって全体を正規化して比較する。

AGC が無効化できなかった録音では、この指標を N/A とする。

> **AGC は録音から確実に検出できる（M4 で検証済み → [7.4](#74-録音品質の推定)）。**
> フレーム音量のダイナミックレンジが **10 dB 未満**なら AGC とみなす。
> 実測では AGC なしが 16.3〜23.5 dB、AGC ありが 5.0〜7.1 dB と完全に分離した。
>
> **実装済み**: `dynamicRangeDb` は `preprocess()`（`worker/ledgerlines_worker/preprocess.py`
> の `dynamic_range_db()`）が算出する値で、定義は「フレーム RMS の 95パーセンタイルと
> 5パーセンタイルの差（dB）」（→ [7.4](#74-録音品質の推定)の式）。ピーク1発に引っ張られる
> `peakDbfs - rmsDbfs`（クレストファクタ）とは意図的に別物にしている。判定は
> `worker/ledgerlines_worker/scoring_constants.py` の `AGC_DYNAMIC_RANGE_DB`（`= 10.0`）
> を `confidence.py` が使い、下回ると `dynamics` を `unavailable`（理由コード
> `AGC_DETECTED`）にする。**この 10.0 は 3.2 の劣化録音デッドゾーン切り替え閾値（14.0）
> とは別の指標・別の目的の値であり、同一の数値として扱わない。**

#### 誤差量

**Step 1: 記譜された目標カーブ**

強弱記号を対数音量スケールに写像する。

| 記号 | 目標値 `L*` |
|---|---|
| ppp | 0.0 |
| pp | 0.14 |
| p | 0.29 |
| mp | 0.43 |
| mf | 0.57 |
| f | 0.71 |
| ff | 0.86 |
| fff | 1.0 |

`cresc.` / `dim.` / ヘアピンは始点と終点の間を線形補間する。
アクセント記号のある音符は `+0.15`、`sf`/`sfz` は `+0.25` する。

小節 *m* の目標音量 `L*(m)` は、その小節に属する参照音符の目標値の平均。

**Step 2: 実測カーブ**

matched 音符の velocity（採譜モデルの推定値）を 0-1 に正規化し、小節平均を取る。

```
V(m) = mean{ velocity(i) / 127 | i ∈ matched, measure(i) = m }
```

**Step 3: アフィン正規化**

演奏全体で `V` を `L*` に最小二乗フィットし、スケールとオフセットを吸収する。

```
V̂(m) = a * V(m) + b      where (a, b) = argmin Σ (a*V(m)+b - L*(m))^2
a は [0.5, 2.0] にクリップする
```

これにより「全体的に大きく弾いた／小さく弾いた」は減点されず、
**強弱の付け方の形**だけが評価される。

> **スケールを制限しない実装は破綻する（M4 で発覚）。**
> 分散の小さい信号にスケールを掛ければ、どんな形でも目標にフィットできてしまうため、
> **強弱を 90% 潰した演奏でも 98.8 点**が出た。
> `a` を [0.5, 2.0] に制限し、次の Step 4 のレンジペナルティを加えることで
> 同じ演奏が **18.5 点**と正しく評価されるようになった。
> → [m4-report.md 4.2](../poc/m4-report.md#42-発見した欠陥--ダイナミクスのアフィン正規化)

**Step 4: 誤差**

強弱の「形」が合っていても、**幅そのものが足りない**場合は減点する必要がある。
これは初中級者に最も多い課題であり、アフィン正規化だけでは検出できない。

```
range_penalty = 0.30 * max(0, 1 - span_est / span_ref)
    span_est = max_m V̂(m) - min_m V̂(m)
    span_ref = max_m L*(m) - min_m L*(m)

e_dyn(m) = max(0, |V̂(m) - L*(m)| + range_penalty - d_d)
d_d = 0.06                            … 記号1段階の約40%までは許容
```

#### スコア

```
dynamics(m) = 100 * exp( -(e_dyn(m) / 0.18)^1 )
```

#### 補助指標：ダイナミックレンジ

減点とは別に、以下を算出してUIに表示する。

```
range_ratio = ( max_m V̂(m) - min_m V̂(m) ) / ( max_m L*(m) - min_m L*(m) )
```

`range_ratio < 0.5` のとき「強弱の幅が楽譜の半分以下です」という指摘を生成する。
**これは初中級者に最も多い課題であり、明示的に検出する価値が高い。**

### 3.5 `articulation` — アーティキュレーション（**MVP から除外**）

> **M4 の検証により、マイク録音では本指標を算出できないと判断した。**
> → [m4-report.md 2.2](../poc/m4-report.md#22-offset-は使えない)
>
> | 実測 | 値 |
> |---|---|
> | 採譜結果の音符長 / ground truth の音符長（中央値比） | **2.3 倍** |
> | offset の系統バイアス | **+300 ms**（ペダルOFF区間でも +148 ms） |
> | 音符長の順位相関（Spearman） | 0.59（短い音符では Pearson 0.26） |
> | レガート断絶の検出 recall | **0.105** |
>
> 採譜モデルが学習した offset は「打鍵を離した時刻」ではなく「響きが減衰しきった時刻」に
> 近く、スケール補正でも順位相関でも救えない。代替案としてレガートの断絶を1ビットで
> 判定する方式も試したが、ground truth では 21.7% の音符が切れているのに採譜結果では
> 2.6% しか切れておらず、判定材料が残らなかった。
>
> 加えて検証データでは音符の 83% がペダル区間にかかっており、
> クラシックではそもそも articulation を評価できる場面が少ない。

**MIDI 入力のテイクでは offset が正確に取れる**ため、将来的に
「MIDI 接続時のみ表示される指標」として復活させる余地は残す。
以下は将来復活させる場合の定義であり、**MVP では算出しない**。

<details>
<summary>将来用の定義（MIDI 入力時のみ）</summary>

#### 誤差量

音符の**実効長比 (Duration Ratio)** を使う。

```
DR(i) = ( offsetSec(i) - onsetSec(i) ) / ( 記譜音価を秒に換算した長さ )
```

記譜音価の秒換算には BeatMap を用いる（テンポ揺れの影響を除去）。

記譜された指示ごとに目標範囲を定める。

| 記譜 | 目標 `DR` | 許容幅 |
|---|---|---|
| スタッカート (`staccato`) | 0.40 | ±0.20 |
| スタッカティッシモ | 0.25 | ±0.15 |
| テヌート (`tenuto`) | 1.00 | ±0.15 |
| スラー内（レガート） | 1.00 | ±0.15（**下限のみ厳しく**：0.85未満で減点） |
| 指示なし（ノンレガート） | 0.75 | ±0.30 |

レガートについては、より本質的な指標として**連続する音のオーバーラップ**を見る。

```
overlap(i, i+1) = offsetSec(i) - onsetSec(i+1)      [秒]
```

- スラー内で `overlap < -0.05秒`（音が切れている）→ レガート不足として減点
- スラー内で `overlap > 0.15秒`（前の音が残りすぎ）→ 濁りとして軽く減点

```
e_art(m) = mean_i( max(0, |DR(i) - DR*(i)| - tol(i)) )  * 0.6
         + mean_i( max(0, -overlap(i) - 0.05) / 0.2 )   * 0.4     … スラー内のみ
```

#### スコア

```
articulation(m) = 100 * exp( -(e_art(m) / 0.25)^1 )
```

#### 精度上の注意

`offsetSec` の推定は `onsetSec` より難しい（特にペダル使用時）。
**ペダルが踏まれている区間ではレガート判定を行わない**（ペダルで繋がるため意味がない）。
その場合、当該小節の `articulation` は「スタッカート系のみ評価」または N/A とする。

</details>

### 3.6 `pedal` — ペダル

**問い**: 踏み替えのタイミングが適切で、濁りが生じていないか。

> **M4 で実用性を確認した。** マイク録音を模した劣化条件でも
> ペダル検出の F1 は **0.81〜0.86** を保った（clean では 0.913）。
> さらにスコアへの影響も小さく、録音条件を変えても `pedal` の変動は
> **-5 点以内**（AGC 込みでも -13.5）と、5指標中もっとも頑健だった。
> → [m4-report.md 2.1](../poc/m4-report.md#21-精度)
>
> 当初「検出精度が最も低い」として重みを 0.08 に抑えていたが、
> 実測ではむしろ頑健な指標であることが分かったため **0.10 に引き上げる**。

#### 評価軸

**A. 記譜との一致（楽譜にペダル記号がある場合）**

```
e_ped_mark = ( |踏み遅れ| + |離し遅れ| の平均秒 ) / 0.25
```

**B. 濁りの検出（記号の有無によらず）**

ペダル区間内で、**和声が変わったのに踏み替えていない**箇所を検出する。

```
1. 参照譜から小節/拍ごとの和音構成音集合を得る
2. ペダル ON 区間で、直前の和音の構成音が新しい和音と 2半音以内で衝突する数を数える
3. e_muddy = 衝突数 / ペダル区間数
```

**C. 踏み替えの遅れ（レガートペダル）**

和声変化点でのペダル UP → DOWN の間隔。
理想は「新しい音の直後に踏み替える」（syncopated pedaling）。

```
e_ped_timing = mean( max(0, |t_pedal_change - t_harmony_change - 0.05| - 0.08) ) / 0.2
```

#### スコア

```
e_pedal = 0.3 * e_ped_mark + 0.5 * e_muddy + 0.2 * e_ped_timing
pedal(m) = 100 * exp( -(e_pedal / 0.4)^1 )
```

記譜にペダル指示がない曲では `e_ped_mark` を除き、重みを再正規化する。

## 4. 小節スコアの合成

```
score(m) = Σ_k ( w_k * metric_k(m) ) / Σ_k w_k        … N/A の指標は除外
```

重みは [2.5節](#25-指標の重み総合スコア) と同一。

### 4.1 総合スコア

```
metric_k = Σ_m ( n(m) * metric_k(m) ) / Σ_m n(m)     … n(m) = 小節mの参照音符数
overallScore = Σ_k ( w_k * metric_k ) / Σ_k w_k
```

**音符数による重み付けの理由**: 全音符1つの小節と16分音符16個の小節を同列に扱うと、
密度の高い難所の影響が過小評価される。

## 5. 指摘 (Issue) の生成

スコアは「どこが」を示すが、指摘は「何が」を示す。

### 5.1 生成ルール

| 種別 | トリガー | 重要度 |
|---|---|---|
| `missed-note` | 1音の抜け | 和音の最高音/最低音なら high、内声なら medium |
| `extra-note` | 余分な音 | velocity ≥ 40 なら medium、未満なら low |
| `timing` | 小節内で \|δ'\| > 0.25拍 の音が2つ以上 | high |
| `timing` (sync) | 両手の同時打鍵の分散 > 60ms | medium。**「アルペジオ癖」として特記** |
| `tempo` | 連続3小節以上で \|ln r\| > 0.12（除外対象外） | high |
| `dynamics` | `range_ratio < 0.5` | medium（曲全体に対して1件） |
| `dynamics` | 小節で \|V̂ - L*\| > 0.25 | medium |
| `pedal` | `e_muddy` が閾値超過 | medium |

### 5.2 グルーピング

同種の指摘が**連続する3小節以上**にまたがる場合、1件に統合する。

```
「17-21小節：一貫してテンポが基準より12%速くなっています」
```

個別に5件出すより、パターンとして1件示すほうが行動につながる。

### 5.3 詳細文の生成

指摘のタイトルはルールベースで生成し、**詳細（原因の推定と対処法）は LLM が生成する**。
LLM には該当小節の構造化データのみを渡し、データにない断定をさせない。
詳細は [AIプロンプト設計](../design/ai-prompts.md) を参照。

## 6. 縦断分析（テイク間比較）

### 6.1 小節別の伸び

```
delta(m) = score_latest(m) - score_baseline(m)
```

`baseline` は比較対象テイク（既定：その曲の最初のテイク）。

### 6.2 停滞小節の検出

直近 N テイク（既定 N=3）について、以下をすべて満たす小節。

```
1. score_latest(m) < 70
2. score_latest(m) - score_oldest(m) < 3
3. すべてのテイクで m ∈ playedRange
4. すべてのテイクで confidence(m) ≥ 0.7
```

条件4が重要。**解析が不安定なだけの小節を「停滞」と誤認しない。**

### 6.3 停滞の分類

停滞小節について、どの指標が原因かを特定する。

```
cause(m) = argmin_k ( metric_k_latest(m) )     … 最も低い指標
```

原因ごとに提案する練習法のテンプレートを変える。

| 原因指標 | 推奨アプローチ |
|---|---|
| `pitch` | 運指の見直し、片手ずつ、ゆっくり確実に |
| `rhythm` | リズム変奏（付点・逆付点）、メトロノームの裏拍取り |
| `tempo` | テンポを 60% まで落として段階的に上げる |
| `dynamics` | 片手ずつ強弱だけを誇張して練習 |
| `pedal` | ペダルなしで和声を確認してから戻す |

### 6.4 進捗の要約指標

| 指標 | 定義 |
|---|---|
| `improvedMeasures` | `delta(m) ≥ 3` の小節数 |
| `stagnantMeasures` | 6.2 の条件を満たす小節数 |
| `regressedMeasures` | `delta(m) ≤ -3` の小節数 |
| `readiness` | 仕上がり度 = `0.7 * overallScore + 0.3 * (100 - スコアの小節間標準偏差 * 2)` |

`readiness` は「平均が高い」だけでなく「ムラがない」ことを評価する。
発表会本番では**最も弱い箇所が全体の印象を決める**ため。

## 7. 信頼度

### 7.1 小節ごとの信頼度

```
confidence(m) = c_transcription(m) * c_alignment(m)
```

| 要素 | 算出 |
|---|---|
| `c_transcription(m)` | その小節の演奏音符の `confidence` の中央値 |
| `c_alignment(m)` | アライメントの局所コスト（DTW の正規化距離）を 0-1 に写像したもの |

### 7.2 閾値と挙動

> **実装上の安全策（Issue #8）を指標別に精緻化した**: 下表の `0.5 / 0.7` は教師評価付き
> データで未較正の設計仮説であり、本番の通過閾値としては使用しない。Issue #8 が定めた
> 一律フェイルクローズ（較正成果物が存在しない、または採譜モデルから音符単位 confidence
> を取得できない場合は `overallScore` と `pitch` / `rhythm` / `dynamics` / `pedal` を
> 一括で判定保留にする）は、当時判明していた情報の範囲では正しい判断だった。
> M4 5章で同一の演奏を clean / 部屋 / スマホ / スマホ+AGC の4条件で再解析し、
> 指標ごとの録音条件への頑健性を実測できたことで、この一律の判断を指標別の判断に
> 置き換えた（`worker/ledgerlines_worker/confidence.py` の `apply_fail_closed_policy`）。

**指標別の扱い（clean 基準の低下幅。M4 5章の実測、条件は 部屋残響 / スマホ / スマホ+AGC）**

| 指標 | 状態 | 低下幅 | 根拠 |
|---|---|---|---|
| `tempo` | `scored` | -2.7 / -1.9 / -3.2 | 3条件とも小さく頑健 |
| `pedal` | `scored`（参照譜にペダル位置が必要 → [worker/README.md](../../worker/README.md)） | -4.5 / -5.0 / -13.5 | AGC下でも頑健 |
| `rhythm` | `scored`（劣化録音ではデッドゾーンを緩める → 3.2） | -11.8 / -6.6 / -14.7 | 劣化条件でも致命的ではない |
| `dynamics` | `scored`。AGC検出時のみ `unavailable`（`AGC_DETECTED`） | -5.7 / -9.0 / **-45.1** | AGCでだけ崩壊する。AGCは確実に検出できる（→ 3.4） |
| `pitch` | **`withheld`**（`PITCH_FORMULA_UNVALIDATED`） | -37.7 / -37.6 / **-50.0** | 録音条件以前に、式自体が採譜ノイズに支配される（下記） |

> **`pitch` を保留する理由は「未較正」ではなく「式が採譜ノイズに支配される」こと。**
> 参照譜1242音符に対し採譜が974音符しか対応付けられなかった（`matchRate` 78%）基準テイクで、
> `extra`（余分な音）が521個生じ、`pitch` は9.99点まで落ちた。
> `e_pitch = (W_MISS * missed + W_EXTRA * extra) / n_ref` の内訳では、`missed` 268個分
> （`W_MISS=1.0`）より `extra` 521個分（`W_EXTRA=0.7`）の寄与が大きく、誤差全体の58%を
> 余分な音が占める。そこに `TAU_PITCH = 0.15` という急な減衰関数がかかるため、
> 78%の音が対応付けられていても指標は壊滅的な値になる。式の再検証（`TAU_PITCH` /
> `W_EXTRA` の再校正）は段3のスコープ（→ 末尾「次の計画」）。

`overallScore` はこの指標別の状態から導かれる（実装値であり別途の閾値ではない）。
`unavailable`（測定対象が存在しない）な指標は加重平均から除外し、残りの重みで
再配分する。一方 `withheld`（測定できるが信頼できない）が1つでも残っていれば、
`overallScore` 自体を `null` にする。`pitch` は常に `withheld` であるため、
この段では `overallScore` は数値化されない（→ 4.1）。

M4 で録音条件への頑健性を確認済みの4指標には理由コード `ROBUSTNESS_VALIDATED` を付ける。
これは「講師評価と順位が一致する」という較正済みの主張ではなく、「録音条件が変わっても
指標が大きく動かない」という頑健性の主張であり、両者を混同しない（→ 8.2 の講師較正の状態）。

以下の測定単位別の信頼度バケットは、上記の指標別ステータスとは別に、小節ごとの
`confidence` を UI バッジに落とし込むための未較正の設計仮説として残す。

| 範囲 | 挙動 |
|---|---|
| `≥ 0.7` | 通常表示 |
| `0.5 - 0.7` | スコアは表示するが「参考値」バッジを付ける。指摘は high のみ生成 |
| `< 0.5` | **スコアを付けない (N/A)**。ヒートマップはグレーのハッチング。AI講評のコンテキストから除外 |

### 7.3 テイク全体の信頼度

```
takeConfidence = mean_m( confidence(m) )
```

`takeConfidence < 0.5` の場合、解析を `failed (ALIGN_FAILED)` として扱い、
採譜結果のみを提示する——という上記の閾値は、7.2 の `0.5 / 0.7` と同様、
教師評価付きデータで較正されていない設計仮説であり、**未実装**のまま据え置く。

> **実装済みの安全網**: `worker/ledgerlines_worker/confidence.py` の `MIN_MATCH_RATE`
> （`= 0.30`）は、上記 `takeConfidence < 0.5` とは別の、より保守的な指標を使う。
> `matchRate`（対応付けられた音符数 / 参照音符数）がこれを下回ると `ALIGN_FAILED` で
> `failed` にする。これは「別の曲の音声を投稿した」ケースに対する安全網であり、
> `takeConfidence` の仮説をもって代替・実装したものではない。`0.30` を `0.5` の
> 仕様を満たしたものとして扱わないこと。

現在の実装は `confidence` を正答確率とは呼ばず、matched 比率と BeatMap アンカー数から
得た**対応品質の観測値**として保存する。教師評価・採譜正解データによる較正が完了するまで、
この値だけで採点可否を決めない。

### 7.4 録音品質の推定

指標のデッドゾーンや N/A 判定を録音品質に応じて切り替えるため、
**音声そのものから品質を推定する**。M4 で実測した特徴量と採譜精度の相関は次のとおり。

| 目的変数 | ダイナミックレンジ | RMS標準偏差 | ノイズフロア |
|---|---|---|---|
| note F1 | +0.47 | +0.46 | -0.48 |
| **velocity 相関** | **+0.92** | **+0.91** | **-0.93** |
| pedal F1 | +0.18 | +0.16 | -0.21 |

```
dynamicRangeDb = percentile95( frameRmsDb ) - percentile5( frameRmsDb )
```

**この式は窓長を決めないと値が定まらない。** 下表の 10 dB / 14 dB は
`poc/scripts/estimate_quality.py` の推定量で実測された値なので、次の4点は閾値と一体である
（実装は `worker/ledgerlines_worker/preprocess.py` の `dynamic_range_db`）。

| パラメータ | 値 | 理由 |
|---|---|---|
| 窓長 | 2048 サンプル（16 kHz で **128 ms**） | 短い窓は1音のアタック/減衰を分解してレンジを系統的に大きく出す。AGC の時定数は数十〜数百 ms なので、短い窓では AGC 録音でも起伏が残り、ゲートを通り抜ける |
| ホップ | 512 サンプル（**32 ms**、窓の1/4＝重なりあり） | 同上。非重複フレームにすると実効的な窓長が変わる |
| パーセンタイルの領域 | **dB 領域**（`frameRmsDb` に対して取る） | 線形 RMS でパーセンタイルを取ってから dB 変換した値とは一致しない |
| トリム | **無音トリム後**（`trim_silence()` の出力） | 先頭・末尾の無音は p5 を押し下げてレンジを過大に見せる。M4 のハーネスはトリム前に適用しているので、この1点だけが意図的な差 |

フレーム RMS は `sqrt(mean(x²) + 1e-10)` で、EPS がフロアになるため無音フレームも除外しない。

| 判定 | 条件 | 挙動 |
|---|---|---|
| **AGC あり** | `dynamicRangeDb < 10` | `dynamics` を N/A にする。ユーザーに AGC の無効化を促す |
| **劣化録音** | `dynamicRangeDb < 14` または推定 SNR が低い | `rhythm` のデッドゾーン `d_r` を 0.045 拍に緩める |
| **良好** | 上記以外 | 既定値を使う |

> **`pitch` のデッドゾーンは録音品質から決められない。**
> note F1 との相関は r ≈ 0.5 にとどまり、音符検出の精度は録音品質より
> **曲の音符密度**に左右される。密な曲は劣化に弱く、疎な曲は強い。
>
> 代替案として、初回利用時に短いキャリブレーション録音を求め、
> その環境での採譜のばらつきを実測してユーザーごとのデッドゾーンを決めることを検討する（M5）。

**録音環境の変化検出**: 前回テイクと `dynamicRangeDb` が 5 dB 以上違う場合、
録音環境が変わったとみなし、テイク間比較に「環境が異なる」注記を付ける（→ [2.6](#26-絶対スコアの扱いm4-の実測を受けて)）。
