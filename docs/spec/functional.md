## 1. プロダクト定義

### 1.1 ワンライナー

> 弾きっぱなしにしない。1曲を仕上げるためのAI練習コーチ。

### 1.2 解こうとしている課題

独学・レッスン通いを問わず、ピアノ学習者は「今日1時間練習した」あとに次の3つが分からない。

1. **どこが悪かったのか** — 自分の耳では気づけないズレ・抜け・強弱の不足がある
2. **前より良くなったのか** — 主観でしか比較できず、成長が実感できない
3. **次に何をすればいいのか** — 「もう一回通す」以外の練習方法を知らない

本プロダクトは、**録音するだけ**でこの3つに答える。

### 1.3 設計原則

| 原則 | 意味 |
|---|---|
| **採点ではなく診断** | スコアは目的ではなく、練習箇所を特定するための手段。総合点よりも「どの小節の何が」を主役にする |
| **リアルタイムを捨てて深さを取る** | 演奏中の負荷ゼロ。演奏後に数十秒かけて深く分析する |
| **ハード非依存** | スマホのマイクだけで成立する。MIDI 入力は「あればより高精度」の位置づけ |
| **自分の楽譜** | 曲は当社が用意しない。ユーザーが持ち込む |
| **表現を評価する** | 音符の正誤だけでなく、テンポ・強弱・アーティキュレーション・ペダルを見る |
| **不確実性を隠さない** | AI採譜には限界がある。信頼度が低い箇所は「自信がない」と表示する（→ 4.4 F-10） |

## 2. ターゲットとユーザーストーリー

### 2.1 ペルソナ

| # | ペルソナ | 状況 | 主要ニーズ |
|---|---|---|---|
| P1 | **独学の再開組**（30-50代） | 昔習っていて再開。先生はいない | 客観的なフィードバック、モチベーション維持 |
| P2 | **レッスン通いの学習者**（小中学生＋保護者） | 週1レッスン、宿題を家で練習 | レッスンとレッスンの間の伴走、先生への共有 |
| P3 | **発表会/コンクール準備者** | 期日が決まっている | 逆算した進捗管理、弱点の潰し込み |
| P4 | **ピアノ講師** | 複数生徒を担当 | 生徒の自宅練習の可視化、レッスン時間の効率化 |

MVP の主対象は **P1・P2**。P4 は「共有される側」として軽量機能のみ提供する。

### 2.2 ユーザーストーリー（MVP）

```
US-01  学習者として、手持ちのMusicXMLをアップロードして曲を登録したい
US-02  学習者として、スマホ/PCのブラウザで演奏を録音したい
US-03  学習者として、練習した小節範囲だけを指定して録音したい
US-04  学習者として、録音後どの小節が弱いかを楽譜上で色で見たい
US-05  学習者として、具体的に何をミスしたか（抜け音・タイミング）を知りたい
US-06  学習者として、前回の録音と比べてどこが良くなったかを知りたい
US-07  学習者として、何度録っても良くならない箇所を教えてほしい
US-08  学習者として、今日やるべき練習メニューを提示してほしい
US-09  学習者として、分析結果についてAIに質問したい
US-10  学習者として、練習の記録（時間・連続日数）を見たい
US-11  学習者として、発表会までの残り日数と仕上がり度を見たい
US-12  学習者として、先生に分析レポートを共有したい
US-13  講師として、共有された演奏を聴き、小節を指定してコメントしたい
US-14  講師として、次回までの課題を登録したい
```

## 3. 用語定義

| 用語 | 定義 |
|---|---|
| **曲 (Song)** | ユーザーが登録した楽曲。楽譜（MusicXML）と目標を持つ |
| **テイク (Take)** | 1回の録音とその分析結果。曲に対して N 件 |
| **小節スコア (MeasureScore)** | 小節ごとの総合点(0-100)と6指標の内訳 |
| **指摘 (Issue)** | 「N小節M拍目の抜け音」のような具体的な事象 |
| **停滞小節 (Stagnant Measure)** | 複数テイクを通じてスコアが改善していない小節 |
| **練習メニュー (Practice Menu)** | AIが生成する、対象小節・テンポ・練習法・時間の組 |
| **信頼度 (Confidence)** | 採譜・アライメントの確からしさ(0-1) |

## 4. 機能仕様

### 4.1 曲管理

#### F-01 曲の登録

| 項目 | 仕様 |
|---|---|
| 入力 | MusicXML (`.xml` / `.musicxml` / `.mxl`)、MIDI (`.mid`) |
| 最大サイズ | 10 MB |
| 必須メタ情報 | タイトル、作曲者 |
| 自動抽出 | 調号、拍子、総小節数、パート構成（MusicXMLから） |
| 任意設定 | 目標テンポ、目標日（発表会日等）、目標メモ、難易度 |
| バリデーション | パース失敗時はエラー詳細を表示。ピアノ2段譜でない場合は警告のうえ受け入れる |

MIDI 入力時は内部で MusicXML 相当の構造（音符・拍子・小節）に変換する。強弱記号・アーティキュレーション記号は MIDI からは取得できないため、該当指標は「評価対象外」として扱う（→ 4.3）。

#### F-02 曲のステータス

`譜読み → 練習中 → 仕上げ → 本番準備OK` の4段階。ユーザーが手動で変更する。
AIは総合スコアと安定度から次段階への昇格を提案するが、自動では変更しない。

#### F-03 曲の一覧・詳細

- 一覧：カード表示。最新スコア、テイク数、目標日までの残日数、ステータス
- 詳細：楽譜＋小節ヒートマップ（最新テイク）、テイク一覧、停滞小節、目標

### 4.2 録音

#### F-04 ブラウザ録音

| 項目 | 仕様 |
|---|---|
| API | `MediaRecorder` + `getUserMedia` |
| 形式 | 優先 `audio/webm;codecs=opus`、Safari は `audio/mp4`（フォールバック） |
| サンプルレート | 44.1kHz 以上を要求。実際の値はメタとして記録 |
| チャンネル | モノラルに変換して送信 |
| 音声処理 | `echoCancellation: false`, `noiseSuppression: false`, `autoGainControl: false` を**必ず指定**（自動ゲインはダイナミクス評価を破壊するため） |
| 最大長 | 15分 |
| 最大サイズ | 100 MB |

> **重要**: ブラウザ既定の AGC/ノイズ抑制は強弱の情報を潰す。無効化できないブラウザでは、ダイナミクス指標を「参考値」として表示する。

#### F-05 録音フロー

```
1. 曲を選択
2. 小節範囲を指定（既定：全体）
3. テンポを指定（既定：曲の目標テンポ）
4. メトロノーム ON/OFF、カウントイン（0/1/2小節）
5. 録音開始 → 波形とレベルメータを表示 → 停止
6. その場で再生して確認 → 「破棄」か「分析する」
7. アップロード → 解析中（非同期） → 完了通知
```

- メトロノームは**ヘッドホン推奨**の注意を表示する（マイクに混入すると採譜精度が落ちる）
- メトロノーム音がマイクに入った場合の除去は行わない。代わりに録音時に混入を検出して警告する

#### F-06 解析ステータス

テイクは以下の状態を持ち、UIはポーリングまたは SSE で追従する。

| 状態 | 意味 |
|---|---|
| `uploading` | クライアントからのアップロード中 |
| `queued` | 解析キュー待ち |
| `transcribing` | 採譜中 |
| `aligning` | 楽譜アライメント中 |
| `scoring` | 指標算出中 |
| `reviewing` | AI講評生成中 |
| `completed` | 完了 |
| `failed` | 失敗（理由コード付き） |

目標処理時間：**3分の演奏を 90 秒以内**（p95）。

#### F-07 解析の失敗ハンドリング

| 理由コード | 状況 | ユーザーへの表示 |
|---|---|---|
| `AUDIO_TOO_QUIET` | 実効レベルが閾値未満 | 「録音音量が小さすぎます。マイクをピアノに近づけてください」 |
| `NOT_PIANO` | ピアノ以外の音が支配的 | 「ピアノの音が検出できませんでした」 |
| `ALIGN_FAILED` | 楽譜との対応が取れない | 「楽譜と演奏が対応しませんでした。小節範囲の指定をご確認ください」＋採譜結果のみ表示 |
| `TOO_MANY_ERRORS` | 一致率が極端に低い | 「譜読み段階かもしれません。範囲を狭めて録音してみてください」 |
| `INTERNAL` | その他 | 「解析に失敗しました」＋再試行ボタン |

`ALIGN_FAILED` の場合も採譜結果（ピアノロール）と音声は保持し、部分的な価値を返す。

### 4.3 分析指標

6指標の**算出定義は [指標定義書](./metrics.md) を正とする**。本書ではUI上の扱いのみ定義する。

| 指標 | 表示名 | MIDI無し(音声のみ)での信頼性 |
|---|---|---|
| `pitch` | 音程正確性 | 高 |
| `rhythm` | リズム | 高 |
| `tempo` | テンポ安定 | 高 |
| `dynamics` | ダイナミクス | 中（AGC・マイク位置に依存） |
| `pedal` | ペダル | 低〜中（**M4で検証。不可なら MVP から除外**） |
| `articulation` | アーティキュレーション | 中（offset 検出精度に依存） |

- 各指標は 0-100。小節単位と曲全体（テイク単位）の両方を持つ
- **総合スコアは6指標の重み付き平均**（重みは [指標定義書](./metrics.md) 参照）
- 楽譜に強弱記号が一切ない場合、`dynamics` は「評価対象外(N/A)」とし、総合スコアの重みから除外する。`articulation`・`pedal` も同様

### 4.4 分析結果

#### F-08 分析結果画面の構成

| ブロック | 内容 | 優先度 |
|---|---|---|
| AI講評 | 見出し・要約・良かった点・改善点 | ★★★ |
| 総合スコアと6指標レーダー | 前回との差分を併記 | ★★★ |
| 楽譜＋小節ヒートマップ | 小節をクリックで詳細 | ★★★ |
| 指摘一覧 | 重要度順。小節ジャンプ可 | ★★★ |
| ピアノロール | 演奏 vs 楽譜の重ね合わせ | ★★ |
| テンポカーブ | 小節ごとの実測BPM vs 目標 | ★★ |
| ダイナミクスカーブ | 実測音量 vs 楽譜の強弱記号 | ★★ |
| 音声プレイヤー | 小節クリックでその位置から再生 | ★★★ |

> **音声プレイヤーの小節シークは MVP 必須。** 「N小節が弱い」と言われても、その音を聴けなければ納得できない。
> PoVモックには存在しないが、実装では中核機能として扱う。

#### F-09 指摘 (Issue)

| 属性 | 内容 |
|---|---|
| 種別 | 抜け音 / 余分な音 / タイミング / 強弱 / ペダル / テンポ |
| 位置 | 小節・拍（必要なら音高） |
| 重要度 | high / medium / low |
| タイトル | 「19小節 2拍目：内声のAが抜けています」 |
| 詳細 | 原因の推定と対処法（AI生成） |

- 1テイクあたり最大 30 件まで表示。超過分は「重要度low」に畳む
- 同一の指摘が連続する小節にまたがる場合はグルーピングする（例：「17-20小節で継続的にテンポが速い」）

#### F-10 信頼度と説明責任

採譜・アライメントの信頼度が閾値未満の小節は、

- ヒートマップ上でグレーのハッチングにし、スコアを付けない
- 「この小節は解析の自信が低いため評価を保留しました」と明示する
- AI講評のコンテキストからも除外する（誤ったアドバイスを防ぐ）

**ユーザーの信頼を失う最大のリスクは「間違った指摘を自信満々にすること」**。保留する勇気を持つ。

### 4.5 履歴と比較

#### F-11 時系列表示

- 総合スコアの推移（テイク単位、日付軸）
- 6指標それぞれの推移
- 目標日がある場合は縦線で表示

#### F-12 テイク A/B 比較

任意の2テイクを選択し、以下を並置する。

- 総合スコアと差分
- 6指標レーダーの重ね描き＋差分数値
- 小節別の差分ヒートマップ（緑＝改善、赤＝悪化）
- テンポカーブの重ね描き

**比較の前提**: 小節範囲が異なるテイク同士は、重複する小節のみで比較する。

#### F-13 停滞小節の検出

本プロダクトの中核的な差別化機能。

**定義**: 直近 N テイク（既定 N=3、最低3テイク必要）において、
以下をすべて満たす小節を「停滞」とする。

1. 最新スコアが 70 点未満
2. 最古テイクから最新テイクへのスコア変化量が +3 点未満
3. その小節が全テイクで演奏範囲に含まれている
4. その小節の信頼度が全テイクで閾値以上（解析不良を停滞と誤認しない）

検出時は「なぜ停滞しているか」の仮説をAIに生成させ、
**通常とは異なる練習法**（テンポを大きく落とす／片手ずつ／リズム変奏／運指の見直し）を提案する。

> 「同じ練習を繰り返しても直らない」ことを検知して介入するのが価値。
> 単に弱点を表示するだけなら競合と変わらない。

### 4.6 AIコーチ

#### F-14 講評の生成

テイク解析完了時に自動生成する。プロンプト仕様は [AIプロンプト設計](../design/ai-prompts.md) を正とする。

出力は構造化JSON：

| フィールド | 内容 |
|---|---|
| `headline` | 一行の要約（例：「左手の安定感が明確に向上しています」） |
| `summary` | 3-5文の全体講評 |
| `strengths` | 良かった点 2-4件 |
| `improvements` | 改善点 2-4件（優先度順） |
| `practiceMenu` | 練習メニュー 2-4件 |
| `context` | 楽曲の様式的背景（作曲家・時代・その曲固有の難所） |

#### F-15 練習メニュー

| 属性 | 内容 |
|---|---|
| タイトル | 「19-20小節の内声を独立させる」 |
| 対象小節 | [19, 20] |
| 練習テンポ | 76 (BPM) |
| 想定時間 | 8分 |
| 練習法 | 具体的な手順 |
| 理由 | なぜこの練習が必要か（分析結果への参照を含む） |

- 合計時間が「今日の練習可能時間」（ユーザー設定、既定30分）に収まるよう生成する
- 各項目は完了チェックが可能。完了状況は次回の講評コンテキストに含める

#### F-16 チャット

- 対象テイク／曲の分析結果をコンテキストとして会話する
- 履歴は曲単位で保持（直近20往復）
- 音楽・練習に無関係な話題は丁寧に断る（システムプロンプトで制御）
- **回答は必ず分析結果に基づくこと**。データにない断定をしない（→ プロンプト設計で制約）

### 4.7 練習ログ・目標

#### F-17 練習ログ

- 日別の練習時間（録音時間の合計＋手動記録）とテイク数
- 連続練習日数（ストリーク）
- 週次の練習時間グラフ

> ゲーミフィケーションは**控えめ**にする。競合が過剰にやっており、
> 中上級者にとってはノイズになる。ストリークと時間の可視化まで。

#### F-18 目標

- 曲ごとに目標日と目標内容を設定
- 残日数、現在の仕上がり度（総合スコア＋安定度）を表示
- 目標日が近く、スコアが伸びていない場合はダッシュボードで警告する

### 4.8 先生との共有

#### F-19 共有リンク

| 項目 | 仕様 |
|---|---|
| 単位 | 曲単位（その曲の全テイクが見える） |
| 認証 | 推測困難なトークンURL（署名付き、既定90日有効） |
| 権限 | 閲覧＋コメント。編集・削除は不可 |
| 内容 | 分析結果、音声、履歴グラフ、コメント、課題 |
| 無効化 | いつでもリンクを無効化できる |

MVP では先生側のアカウント登録を必須にしない（レッスン現場の摩擦を減らすため）。
コメント時に表示名の入力のみ求める。

#### F-20 コメント

- 小節にピン留め可能（`measure: number | null`）
- テイクに紐付け可能（`takeId: string | null`）
- スレッド形式。学習者側からも返信できる

#### F-21 課題（宿題）

- タイトル、詳細、期日、状態（未着手/対応中/完了）
- 先生・学習者の双方が作成できる
- ダッシュボードに期日の近い課題を表示する

### 5.1 レスポンシブ方針

| 幅 | 方針 |
|---|---|
| < 640px | 録音・分析結果の閲覧に最適化。サイドナビはボトムタブへ。楽譜は横スクロール |
| 640-1024px | 2カラム |
| > 1024px | サイドナビ＋3カラムまで |

録音はスマホでの利用が主になる想定のため、**SC-05 はモバイルファースト**で設計する。

## 6. 非機能要件

### 6.1 性能

| 項目 | 目標 |
|---|---|
| 解析時間（3分の演奏） | p50 45秒 / p95 90秒 |
| 画面初期表示 (LCP) | p75 2.5秒以内 |
| 分析結果画面の操作応答 | 100ms以内 |
| 同時解析ジョブ | 初期20並列まで自動スケール |

### 6.2 可用性・信頼性

- 目標稼働率 99.5%（MVP）
- 解析ジョブは最低1回実行を保証。失敗時は最大2回まで自動リトライ
- 音声とテイクのメタデータは、解析が失敗しても失われない

### 6.3 セキュリティ・プライバシー

| 項目 | 方針 |
|---|---|
| 認証 | Microsoft Entra External ID |
| 音声データ | ユーザーに帰属。既定で**モデル学習に使わない**。同意した場合のみ利用 |
| 楽譜データ | ユーザーがアップロードしたものを他ユーザーに配信しない |
| 保存 | 保管時暗号化。Blob は private、アクセスは短命 SAS 経由 |
| 削除 | 曲・テイクの削除で音声・分析結果を物理削除（30日の猶予後） |
| 共有リンク | 署名付き。有効期限あり。無効化可能 |
| LLM | Azure AI Foundry。入力を学習に使わない構成であることを明示する |

### 6.4 コスト

MVP の目標は **月間アクティブ1,000ユーザー・1人あたり月20テイクで、月額運用費 10万円以内**。
内訳の試算は [アーキテクチャ設計](../design/architecture.md) に記載する。

コスト最大要因は解析ワーカーの計算資源。以下で抑制する。

- GPU は必須ではない構成を第一候補にする（CPU推論でも 3分/90秒 を狙う）
- Container Apps のゼロスケールを活用する
- LLM 呼び出しは1テイクにつき1回（講評）。チャットは都度

### 6.5 対応環境

| 種別 | 対応 |
|---|---|
| ブラウザ | Chrome / Edge / Safari の最新2バージョン、iOS Safari、Android Chrome |
| 言語 | 日本語（MVP）。英語は Phase 2 |
| オフライン | 非対応（Phase 2 で録音のみオフライン対応を検討） |

## 7. 受け入れ基準（MVP完了条件）

```
AC-01  MusicXMLをアップロードして曲を登録でき、楽譜が正しく描画される
AC-02  ブラウザで録音し、アップロードから解析完了まで自動で進む
AC-03  3分の演奏の解析が p95 90秒以内に完了する
AC-04  ミスタッチを意図的に入れた演奏で、該当小節のスコアが有意に下がる
AC-05  小節ヒートマップの色と、実際の演奏の弱点が人間の判断と一致する（7割以上）
AC-06  音声プレイヤーで小節をクリックすると±0.3秒以内でシークする
AC-07  2テイクの比較で、改善した小節が緑、悪化した小節が赤で表示される
AC-08  3テイク以上あるとき停滞小節が検出され、通常と異なる練習法が提案される
AC-09  AI講評が分析結果と矛盾しない（9割以上）
AC-10  共有リンクを開くと、ログインなしで分析結果を閲覧しコメントできる
AC-11  解析に失敗した場合、理由が日本語で表示され再試行できる
AC-12  信頼度の低い小節が明示され、スコアが付かない
```

### 7.1 AC-05 / AC-09 の検証方法

| 基準 | 方法 |
|---|---|
| AC-05 | ピアノ講師3名に、同一音源を聴いて「弱い小節 上位5つ」を挙げてもらい、システムのワースト5との一致率を測る。3名の平均で70%以上 |
| AC-09 | 30件のテイクについて、AI講評の各文が分析データと矛盾しないかを人手でチェック。矛盾率10%未満 |

## 8. リスクと対応

| # | リスク | 影響 | 対応 |
|---|---|---|---|
| R1 | **マイク録音のみでのペダル検出が実用精度に達しない** | 指標1つが使えない | M4で検証。不可なら MVP から除外し、MIDI接続時のみ提供 |
| R2 | アコースティックピアノの調律ずれ・環境ノイズで採譜精度が落ちる | 全体の信頼性 | M4で多様な音源を検証。信頼度スコアで保留する仕組みで緩和 |
| R3 | ブラウザのAGCを無効化できず、ダイナミクス評価が破綻する | 指標1つが劣化 | 無効化可否を検出し、不可なら「参考値」表示に落とす |
| R4 | AI講評が分析結果と矛盾する（ハルシネーション） | 信頼失墜 | 構造化データのみを根拠にする制約、出力の自動検証、AC-09の継続測定 |
| R5 | ルバートを「テンポが不安定」と誤判定する | 中上級者に不評 | テンポ指標は「意図的な揺れ」を区別する設計にする（[指標定義](./metrics.md) 参照） |
| R6 | 解析コストが想定を超える | 事業性 | CPU推論の実現性をM4で確認。無理ならフリーミアムの回数制限で調整 |
| R7 | 楽譜と演奏の小節対応がずれる（繰り返し・ダカーポ） | 分析全体が無効 | MusicXMLの繰り返し記号を展開した「演奏順」を正とする。M4で検証 |
