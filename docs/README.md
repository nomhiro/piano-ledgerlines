## この設計の中心にある考え方

### 1. スコアは目的ではなく、会話の材料

数値だけを見せると「点数を上げるゲーム」になる。指標は常に
**「どの小節が」「なぜ」「次に何をするか」**とセットで提示する。
（[評価指標定義 0.1](./spec/metrics.md#01-スコアは目的ではない)）

### 2. 楽譜どおり = 良い演奏ではない

ずれを「誤り / 揺らぎ / 表現」の3階層で扱い、**表現は減点しない**。
ルバートを機械的に減点する設計は、音楽的な演奏ほど低評価になる。
（[評価指標定義 0.2](./spec/metrics.md#02-正解は楽譜そのものではない)）

### 3. 測れないものは測れないと言う

マイク録音の限界（特にペダル）を隠さない。信頼度が閾値未満の小節は
スコアを付けず **N/A** とし、AI にも「言及するな」と明示する。
（[評価指標定義 7章](./spec/metrics.md#7-信頼度)）

### 4. AI に判断させない

LLM には**判断済みのラベル**を渡し、良し悪しの判定はさせない。
出力は Structured Outputs で拘束し、さらに機械検証（V1〜V9）を通す。
最大のリスクは「分析結果と矛盾する講評」。
（[AIプロンプト設計 1.1](./design/ai-prompts.md#11-最大のリスク)）

## 設計上の要となる技術判断

| 領域 | 判断 | 根拠 |
|---|---|---|
| 採譜 | ByteDance `piano_transcription_inference` を採用（M4 で確定） | velocity 回帰と sustain pedal 検出を持つ。M4 の実測で note F1 0.98（クリーン）/ 0.83〜0.89（劣化） |
| アライメント | **イベント列 DTW（Jaccard距離）→ イベント内マッチング → 秒ベース近傍探索** | M4 で F1 0.962、弾き逃しの誤検出 0.4% を達成。当初案のクロマ DTW は不要と判明 |
| リズム評価 | **BeatMap** で絶対時刻を拍に変換してから評価 | テンポ揺れを除去しないと rhythm と tempo が分離できない |
| テンポ基準 | 目標テンポではなく**実演奏の中央値** | 全体的に遅く弾くことは「不安定」ではない |
| ダイナミクス | アフィン正規化 + **スケール制限 + レンジペナルティ** | 正規化だけでは強弱を潰した演奏が満点になる（M4 で発覚し修正） |
| 指標の数 | **5指標**（articulation を除外） | マイク録音では消音時刻が信頼できない（M4 実測でバイアス +300ms） |
| スコアの提示 | **絶対値ではなく前回比を主役に** | 録音環境だけで総合スコアが 89 → 61 動く（M4 実測） |
| Cosmos PK | `takes` は `/songId`（`/userId` ではない） | 履歴比較が曲内で完結するため |
| 非同期処理 | Storage Queue + Container Apps Job（KEDA、ゼロスケール） | 負荷が断続的。常時課金を避ける |
| 解析のUX | **数分かかる前提で、完了を通知する設計** | CPU 推論の RTF は 1.25。3分の曲に約4.3分（M4 実測） |
| 結果の提示 | スコア確定時点で画面を出し、AI講評は後から差し込む | 講評の生成を待たせない |

## M4 で検証した前提

| # | 論点 | 結果 |
|---|---|---|
| 1 | CPU 推論で採譜が実用速度に収まるか | **△ 動くが速くはない。** RTF 1.25（4 vCPU）。3分の曲に4.3分。vCPU を増やしても改善しない（メモリ帯域律速）。**解析は非同期・通知前提に設計を変更**。コスト試算は 8.5万→16万円に修正され、ONNX 化が必須課題になった |
| 2 | マイク録音のみでペダル指標が実用精度に達するか | **○ 達する。** 劣化条件でも検出 F1 0.81〜0.86、スコア変動 -5点以内。**MVP に採用し、重みを 0.08 → 0.10 に引き上げた** |
| 3 | 自前2段階DTW の精度 | **○ 十分。** F1 0.962、弾き逃しの誤検出 0.4%。外部ツールとの比較は不要と判断。ただし**弾き直しには原理的に非対応**で M5 の課題 |
| 4 | 減点関数のパラメータが人間の評価と相関するか | **△ 一部のみ。** 12種類の摂動に対し5指標が単調かつ直交的に反応することは確認。**講師評価との相関は未検証** |
| 5 | （新規発見）articulation を音声から評価できるか | **× 不可能。** オフセットに +300ms のバイアス、音符長が2.3倍。代替案（レガート断絶の検出）も recall 0.105 で不成立。**MVP から削除** |
| 6 | （新規発見）絶対スコアは環境をまたいで比較できるか | **× できない。** 同一演奏で録音条件を変えると総合 89 → 61、pitch 85 → 35。**UI 設計を前回比中心に変更** |

詳細は [M4 検証レポート](./poc/m4-report.md)。

## M5 に持ち越した未検証事項

| # | 論点 | 影響範囲 |
|---|---|---|
| 1 | **初中級者の演奏（止まる・弾き直す）をアライメントできるか** | 主要ターゲットに直撃。DTW の単調性仮定を破る必要がある。**最重要** |
| 2 | ONNX / int8 量子化で採譜を高速化できるか | コストの64%を占める。目標コスト達成の前提 |
| 3 | 同一環境で繰り返し録った場合、スコアの差分は安定するか | 「前回比を主役にする」設計の前提。M4 では未実証 |
| 4 | 講師評価との順位相関 | 減点関数のパラメータ較正に必要 |
| 5 | 実 MusicXML を参照譜にした場合の挙動 | M4 では ground truth MIDI から参照譜を合成した |
| 6 | ピアノ以外の音（メトロノーム・話し声）の混入 | 実練習環境では頻出 |

## PoVモックとの関係

`src/` 配下の PoV モックは M2 の成果物で、**画面と体験の検証**が目的です。
本設計はモックの型を拡張したものになっています。

主な差分：

- `Score` が `number | null`（N/A 対応）
- `MeasureScore.confidence` の追加
- `scoreMeasure`（楽譜上の小節番号）の追加 — 繰り返し展開への対応
- `TakeStatus` / `FailureCode` の追加 — 非同期解析への対応
- ピアノロールをテイクから分離（[API仕様 5.5](./spec/api.md#55-大きなデータ)）

移行方針は [API仕様 8章](./spec/api.md#8-povモックとの対応) を参照。
